Ты — senior Rust/desktop-разработчик. Построй кросс-платформенное десктопное приложение ClipSync, которое синхронизирует системный буфер обмена между компьютерами в одной локальной сети. Когда пользователь копирует текст или изображение на одной машине, это содержимое автоматически появляется в буфере обмена на других машинах (готово к вставке через Ctrl+V) — без ручных действий.
Начни с Phase 0 (MVP). Не реализуй Phase 1–3, пока я явно не попрошу. Сначала покажи план работ и структуру проекта, затем реализуй MVP инкрементально.
Технологический стек (решено, не предлагай альтернатив)

Framework: Tauri 2.x (Rust-бэкенд + минимальный веб-фронт для UI настроек/паринга).
Буфер обмена: крейт tauri-plugin-clipboard (community, обёртка над clipboard-rs) — он умеет text/html/image/files и мониторинг изменений на Windows/macOS/Linux. Если плагин не подойдёт по API — используй clipboard-rs напрямую.
Автодискавери: mdns-sd (регистрация и поиск сервиса _clipsync._tcp.local).
Async-runtime: tokio.
Транспорт: WebSocket поверх TCP (tokio-tungstenite) с фреймингом сообщений. QUIC (quinn) — допустимая альтернатива, если так проще для крупных бинарных полезных нагрузок; выбери одно и обоснуй.
Сериализация: serde + MessagePack (rmp-serde) или bincode — для эффективной передачи бинарных данных (картинок).
Шифрование: TLS (rustls) с self-signed сертификатом и pinning, либо PSK-шифрование (chacha20poly1305/aes-gcm) на ключе, выведенном из кода паринга. Трафик буфера обязан быть зашифрован.
Трей и автозапуск: встроенный tray API Tauri + tauri-plugin-autostart.


⚠️ Версии крейтов проверь сам по актуальному состоянию crates.io/docs — не полагайся на номера версий из этого промпта.

Окружение и масштаб

Целевая ОС для MVP: только Windows 10/11. Разработка ведётся на Windows.
Клиентов мало: ровно 2 машины на старте (но архитектуру держи расширяемой до mesh).
Обе машины в одной L2-подсети (mDNS работает в пределах broadcast-домена).
UX: содержимое кладётся в системный буфер принимающей машины (не автовставка в активное окно).

Как это работает (поток данных)

На каждой машине запущен watcher буфера обмена.
Локальное изменение буфера → определить тип и взять самое «богатое» представление → сериализовать (тип + payload + хэш + origin) → отправить подключённым парам.
Пир получает сообщение → пишет содержимое в свой локальный буфер.
Защита от петель (КРИТИЧНО): при записи удалённого содержимого в локальный буфер watcher сработает снова и попытается переотправить то же самое — это бесконечное эхо. Реши через guard: храни last_applied_hash; когда применяешь удалённое содержимое, запоминай его хэш и в течение короткого окна игнорируй локальное событие с тем же хэшем. Дополнительно — дедуп по хэшу контента (не отправлять, если совпадает с последним отправленным/применённым).

Функциональные требования — Phase 0 (MVP)

 Приложение живёт только в системном трее: при запуске сворачивается в трей, окна в панели задач нет, закрытие окна настроек НЕ завершает процесс (приложение продолжает работать в фоне и синхронизировать буфер). Завершение — только через пункт «Выход» в меню трея.
 Меню трея: статус подключения, список пиров, тумблер Pause/Resume sync, открыть настройки/паринг, выход.
 Автодискавери пиров через mDNS (сервис _clipsync._tcp).
 Паринг: машины синхронизируются только после паринга по коду (6–8 знаков) → из кода выводится общий ключ. Это не даёт случайной машине в LAN получать твой буфер. Запарированные пиры сохраняются в allowlist.
 Зашифрованное P2P-соединение между двумя запарированными пирами.
 Синхронизация текста (UTF-8) в обе стороны.
 Синхронизация изображений (минимум PNG/растровые данные из буфера; типичный кейс — скриншот) в обе стороны.
 Защита от петель + дедупликация по хэшу.
 Дебаунс событий буфера (~150–300 мс): одно копирование может породить несколько событий (особенно для картинок с несколькими форматами) — читать один раз после паузы.
 Лимит размера payload (конфигурируемый, дефолт ~25 МБ): больше лимита — пропустить и показать уведомление в трее.
 Конфиг (ключ паринга, allowlist пиров, лимит размера, включённые типы данных) сохраняется в app config dir.
 Корректная переустановка соединения при разрыве (reconnect с backoff).
 CI на GitHub Actions собирает Windows-инсталляторы и публикует их как скачиваемые artifacts (детали — раздел «CI/CD»).

Критичные технические моменты (вынеси в комментарии/тесты)

Защита от петель и дедуп по хэшу — см. выше, это главный источник багов.
Дебаунс событий watcher.
Выбор представления: если в буфере одновременно несколько форматов — синхронизируй одно «лучшее». Приоритет для MVP: image → text. Сделай это конфигурируемым.
Безопасность LAN: общая сеть небезопасна по умолчанию. Обязателен паринг + шифрование транспорта; не принимай данные от незапарированных пиров.
Приватность: в MVP не пиши историю буфера на диск (буфер часто содержит пароли). Максимум — опциональный in-memory список последних элементов.

Нефункциональные требования

Низкий idle-расход CPU/RAM (это всегда-работающий демон).
Чистая модульная структура, обработка ошибок без unwrap() в рантайм-путях, логирование (tracing).
Понятные сообщения об ошибках подключения/паринга в UI.

CI/CD (GitHub Actions)
Настрой автоматическую сборку: при каждом пуше проект собирается сам, а я могу скачать готовые инсталляторы и поставить их на тестовые хосты вручную.
Требования:

Workflow .github/workflows/build.yml. Триггеры: push в main, pull_request, workflow_dispatch (ручной запуск).
Runner: windows-latest (для MVP только Windows; матрицу под macOS/Linux добавим в Phase 2).
Шаги: checkout → setup Node → Rust toolchain (stable) → кэш Rust-зависимостей (Swatinem/rust-cache, workspaces: src-tauri) → установка зависимостей фронта → tauri build.
Опубликовать собранные инсталляторы как workflow-artifact через actions/upload-artifact (скачиваются со страницы запуска в Actions). Пути сборки Tauri под Windows:

NSIS-инсталлятор: src-tauri/target/release/bundle/nsis/*.exe
MSI-инсталлятор: src-tauri/target/release/bundle/msi/*.msi


(Опционально) отдельный release-workflow на пуш тега v*: использовать tauri-apps/tauri-action, чтобы создать GitHub Release и приложить к нему инсталляторы — для версионной раздачи.

Скелет (проверь актуальные версии экшенов; команду сборки фронта подгони под выбранный пакет-менеджер — npm/pnpm/yarn):
yamlname: build
on:
  push:
    branches: [ main ]
  pull_request:
  workflow_dispatch:

jobs:
  build:
    runs-on: windows-latest
    steps:
      - uses: actions/checkout@v4
      - uses: actions/setup-node@v4
        with: { node-version: 20 }
      - uses: dtolnay/rust-toolchain@stable
      - uses: Swatinem/rust-cache@v2
        with: { workspaces: src-tauri }
      - run: npm ci
      - run: npm run tauri build
      - uses: actions/upload-artifact@v4
        with:
          name: clipsync-windows-installers
          path: |
            src-tauri/target/release/bundle/nsis/*.exe
            src-tauri/target/release/bundle/msi/*.msi
Замечания:

Инсталляторы в MVP не подписаны → на тестовых хостах Windows SmartScreen покажет предупреждение при установке. Для тестов это нормально; подпись кода (code-signing сертификатом) и подпись Tauri-апдейтера — отдельная задача на потом.
Если в tauri.conf.json задан beforeBuildCommand, отдельный шаг сборки фронта не нужен — tauri build соберёт фронт сам.
Артефакты workflow хранятся ограниченное время (по умолчанию ~90 дней) — для долгой/версионной раздачи используй release-workflow с тегами.

Критерии приёмки MVP

Две Windows-машины в одной LAN находят друг друга после паринга по коду.
Копирование текста на машине A → доступно через Ctrl+V на машине B за ~1 с.
Копирование изображения (например, скриншота) на A → вставляется на B.
Нет бесконечного эхо-цикла синхронизации.
Payload больше лимита пропускается с уведомлением в трее.
Sync ставится на паузу и снимается с паузы из трея.
Трафик зашифрован; незапарированная машина в LAN не может прочитать содержимое буфера.
